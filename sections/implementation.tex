\section{Implementation}\label{impl}
\subsection{Technologies used}
Backend technologies used include Pigeon \parencite{pigeon} for \acrfull{peg} scripting, which generated a Go file; net/http Go package \parencite{net-http} to handle client-server communication; html/template Go package \parencite{html-template} to provide HTML output to the client; and os/exec \parencite{os-exec} to compile \latexspaced via the \acrfull{cmd}.

Frontend technologies used include Tailwind CSS \parencite{tailwind} to avoid repetition of \acrfull{css} through use of components and Flowbite \parencite{flowbite} to expand on its base components library.

Additionally, Go, \acrfull{html}, Pigeon \parencite{pigeon} \acrshort{peg} script, and \acrshort{css} were the languages used in the project.

Lastly, \lintexspaced implements a server-client relationship. This means the client sends a request for resources and the server provides those resources if it decides to accept the request, or provides an error. The net/http Go package \parencite{net-http} requires all directories and files on the server be explicitly provided, and applies validation to the server route taken, both of which acts as an additional security meaasure.

\subsection{PEG parsing}\label{impl:peg_parsing}
\figureref{figure:latex_doc_parsing_structure} showcases the order in which \lintexspaced parses the document in its \acrshort{peg} script. The \acrshort{peg} script can be found in \cref{appendix:peg_script}.

There are a few key points in reading this diagram:
\begin{itemize}
    \item Prerequisite is the chosen name to reference content before the document class in our context.
    \item The line construct immediately after the document class must have the identifier `documentclass'.
    \item The topmost layer for the document content must conform to a group construct with the identifier `document'.
    \item Components is an interface that can conform to either group or line constructs, following the Composite design pattern \parencite{composite_design_pattern}.
    \item A line construct references a singular \latexspaced line, such as \verb|\includegraphics[alt={Some alt text}]{image.png}|. This does not reference any \latexspaced line that is involved in a grouping construct.
    \item A group construct references a named group starting with \verb|\begin{<name>}| and ending with \verb|\end{<name>}| with \verb|<name>| swapped for the group identifier. Other methods to reference group constructs are not included in \lintex 's parsing.
    \item Anonymous, or unnamed, group constructs are not handled by \lintex.
    \item The content between line or group constructs, that do not conform to either, is mostly ignored. For example, plain text.
\end{itemize}

\input{figures/latex_doc_parsing_structure}

In the creation of this \acrshort{peg} script, a top-down approach was taken. This involved looking at the general structure of a \latexspaced document and breaking it down further continuously until a group construct or a line construct is reached, depending on the context.

\input{figures/latex_line_parsing_structure}

\figureref{figure:latex_line_parsing_structure} showcases the general structure of a line construct. A similar structure was utilised for group constructs, with the difference that the first required argument, an argument surrounded by curly braces (`\{\}'), contained the group identifier. A stack was utilised in a group's depths management and error identification. A generic class, a class that can have its typing defined during program execution, was utilised with its typing passed during construction of the stack. This provided the advantage of making the stack code reusable for different underlying typings.

As the final parsing element, argument handling handled both optional (referenced as `OptionArgument' in program code) and required (referenced as `ClassArgument' in program code) arguments separately, while ensuring they conform to the same argument interface. Additionally, an argument type whose inner content aligns with a key-value pairing was created to handle some arguments in more depth. A key-value pairing references having a key and value separated by an equal sign (`=') creating a pair, and consequently having all pairs separated by a comma (`,').

\subsection{Verification \& validation}
Verification took advantage of Go's strictly typed nature, such that a custom data structure or interface was created for every reasonable context. For example, there is an interface, `IDocument', and a `Document' class that conforms to it, both of which are used in the handling of the overall document structure being enforced. However, minimal verification of the document content is applied at this stage, as that is outwith the scope of this project as defined in \fullref{conc:project_limits}.

Validation is applied through the Adapter class \parencite{adapter_design_pattern}, `AccessibleDocument', with its checks over the document, such as verifying the document contains tagging for its whole document and tables, as well as ensuring all images contain \gls{alt_text} unless otherwise specified.
